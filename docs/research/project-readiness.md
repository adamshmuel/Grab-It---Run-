# מוכנות לפרויקט: ידע, כלים וראיות

**עדכון הגדרות, 25/10/2026:** [חבילת שיפורי V1](../specs/v1/improvements.md) הושלמה לבדיקה של אדם, עם [חישוב מסעות](v1-improvement-balance.md) ותנאי קבלה. אין בכך מימוש, הרצת Studio חדשה או סגירת הכשלים בדוח הזה.

**עדכון נוכחי: 25/10/2026. V1 נכשלה מול מטרות המשחק. המיפוי והראיות הטכניות נשמרים בהמשך.**

[אבחון הכשל המוסכם](v1-design-failure-review.md) מתעד את הכשלים שאדם אישר. תחום התכנון והערכת המוצר אינו מוכח מעצם הצלחת הפיתוח וה־tests. נוספו בקרות מחייבות בתוך rules/sdd.md; יעילותן עדיין צריכה להיבדק בהמשך העבודה.

המצב העדכני מופיע בתוך [מפת הקבלה](v1-acceptance-status.md) ובתוך [בדיקות ההמשך של V1](v1-validation.md): קוד פעיל, שתים־עשרה חבילות tests, השוואה חזותית עצמאית מול שלושה משחקים, מסלולי מקלדת ו־touch ובדיקות עם clients אמיתיים. מדידת 600 שניות בגרפיקה 5, בגודל 1280 על 720 ועם שמונה שחקנים עברה בחלון שנבחר מראש. [הבדיקה מול המטרות](v1-goals-review.md) מציינת את גבולות התוצאות.

הפער לקבלה אינו רק בדיקה עם אנשים: יש כשל ידוע בהתפתחות האתגר, בתגמול וברצף אחרי מיצוי החפצים. נדרשת הסכמה על תיקון ההגדרות לפני חידוש הקבלה; חמישה משתתפים והעדפתם עדיין לא נבדקו. תנועה ואיסוף בשני מגעים עברו בשני פרופילי הטלפון. לאחר אישור אדם הופעלה גישת API במשחק בלבד; [שמירה וכניסה מחדש בענן](evidence/v1/cloud-save-rejoin.json) עברו בשני שרתי Solo מול DataStore נפרד. נתוני הבדיקה והסימון הזמני נוקו, ו־Studio רגיל חזר לזיכרון מבודד. אין קבלה כוללת. הטבלה הראשונית והסעיפים ההיסטוריים להלן מתארים את מצב 22/10 לפני המימוש, ואינם מצב נוכחי.

המסמך מרכז את ששת התחומים שאדם הגדיר ואת ארבע התוספות שסוכמו. הוא בודק מה יש בידינו כדי להתקדם לעבר [מטרות הפרויקט](../specs/project-goals.md), ומה עדיין לא הוכח. הוא אינו implementation plan ואינו אישור לכתיבת קוד.

## תמונת המצב

בתאריך 25/10/2026 אדם אישר [תהליך מחייב להערכת החוויה](../../rules/game-experience-validation.md). פירוט הבדיקות מזהה בתיעוד את כשלי V1 הידועים ושומר בנפרד את הסעיפים שאדם בחר לשמר. זו בדיקת שימוש ראשונית מול מידע קיים, ולא הוכחה ליכולת לספק משחק מהנה או לגלות כל כשל עתידי. השוואה מלאה לרף חווייתי של המתחרים והערכת השיפורים טרם הושלמו.

**יש סביבת בסיס עובדת ויכולת מוכחת לבצע מחקר מתחרים וליצור מסמכים קריאים. עדיין אין הוכחה ליכולת לספק משחק שלם שעומד במטרות.** הראיות לכך צריכות להצטבר במהלך עבודה שתאושר, ולא ניתן להחליף אותן בהצהרה על ידע או בנוכחות של skills.

| תחום | מה כבר יש | מה עדיין חסר |
| --- | --- | --- |
| 1. עיצוב המשחק והעיצוב החזותי | gameplay מאושר ומחקר חזותי על משחק דומה | השוואה רחבה יותר וקריטריונים לאיכות שלנו |
| 2. תכנות ואיכות קוד | כלי עיצוב, lint ויצירת מקום פועלים | קוד משחק שנבדק, type checking וביצועים מוכחים |
| 3. כלי בדיקה והיקף בדיקות | בדיקת סביבה בסיסית ותיעוד בדיקות | כיסוי התנהגות, כמה שחקנים ומסלול בדיקה חוזר |
| 4. מסמכים לפי המטרות | מטרות, gameplay מאושר וטיוטות V1 עם קשר למטרות ודוגמאות קבלה | אישור הטיוטות והוכחת הבנתן בידי אדם |
| 5. משימות קטנות ושמירת context | מסמכים נפרדים והיסטוריית commits | הוכחה שהפירוק שומר רצף ומונע עבודה חוזרת |
| 6. מעקב אחר התוכנית | כללי עבודה, אישורים וראיות מקומיות | עדיין אין תוכנית או מעקב ביצוע שנוסו |
| 7. הבנת השחקנים וההנאה | שאלות לבדיקה מתוך מסמך gameplay | תצפיות על אנשים שמשחקים |
| 8. הבנת הפלטפורמה | בדיקת חיבור ותיעוד אבטחה ובדיקות | התנהגות בטוחה ועקבית במשחק שלנו |
| 9. חשיבה מוצרית ועסקית | מטרות מוסכמות ודוגמת מוצרים של מתחרה | מדדי הצלחה, מודל הכנסות והיקף מוצר מאושרים |
| 10. תחזוקה ושימוש חוזר | Git, כללים ומיומנויות זמינות | רכיבים שבאמת הוכיחו צורך משותף ותחזוקה פשוטה |

המצבים בטבלה אינם ציוני מומחיות או אחוזי מוכנות. בכל תחום מפורטים בהמשך הממצא, המקור והראיה שתידרש כדי לסגור את הפער.

## 1. עיצוב המשחק והעיצוב החזותי

**נדרש:** לחבר את החלטות המשחק לפשטות, לקצב, לרצון לעוד סיבוב ולרמת הצגה מתאימה. להבחין בין מכניקות לבין גרפיקה.

**זמין והודגם:** המיומנות roblox-trends וכלי חיפוש ותמונות. [מחקר המשחק הדומה](escape-tsunami-for-brainrots.md) הדגים איסוף נתונים ושלוש תמונות gameplay, הורדה, צפייה ושמירת מקורות. [מסמך gameplay המאושר](../specs/v1/gameplay.md) מגדיר את הבחירה בין חזרה בטוחה לבין איסוף נוסף.

**מקורות שנבדקו:** [Core loops](https://create.roblox.com/docs/production/game-design/core-loops) ותמונות מתוך מדריכי [LDPlayer](https://www.ldplayer.net/blog/escape-tsunami-for-brainrots-roblox-guide.html?n=60000) וכן [All Things How](https://allthings.how/escape-tsunami-for-brainrots-all-events-and-spawn-mechanics/). הצילומים היסטוריים ותאריך הצילום המדויק אינו ידוע.

**הפער והראיה הנדרשת:** משחק אחד אינו מייצג את השוק. נדרשים רפרנסים נוספים שמתאימים למכניקות שלנו, והסבר מה נאמץ מבחינת בהירות והצגה ולמה. אנימציה וקצב לא הוכחו בתמונות. אין בסיס לקביעה שהעיצוב גרם להצלחת המתחרה.

## 2. תכנות ואיכות קוד

**נדרש:** ידע בשפת Luau ובמבנה הקוד של Roblox; מניעת שכפול מיותר, קוד שאינו בשימוש ותקלות במשאבים. טענות על יעילות צריכות להישען על מדידה.

**זמין והודגם:** המיומנויות roblox-dev-skill, roblox-docs וכן roblox-code-review זמינות בפרויקט. היום אומתו מחדש Git 2.54.0, Rojo 7.7.1, StyLua 2.5.2 וכן Selene 0.32.0. קובצי בדיקת הסביבה עברו בדיקת עיצוב וכן lint; יצירת קובץ מקום מקומי עברה.

**מקורות שנבדקו:** [מערכת הטיפוסים של Luau](https://luau.org/types/) וכן [ביצועי Luau](https://luau.org/performance/). מערכת הטיפוסים יכולה לזהות סוגי טעויות בזמן כתיבה; זו אינה הוכחת נכונות מלאה. המקור הישן typecheck מפנה כעת לעמוד types.

**הפער והראיה הנדרשת:** לא קיים עדיין קוד gameplay. בדיקת Selene אינה type checking, ופקודת luau-analyze לא נמצאה בבדיקת הסביבה הקודמת. טרם הודגם מסלול בדיקת טיפוסים לפרויקט. היכולת הנדרשת תוכח בשינויים קטנים שעוברים tests וכן code review, ובמדידה כשיש חשש לביצועים. אין להסיק מומחיות מתקדמת משני מודולי בדיקה קטנים.

## 3. כלי בדיקה והיקף בדיקות

**נדרש:** לבחור סוג בדיקה לפי ההתנהגות והסיכון: חישובים בנפרד, חיבור בין מערכות, וסיבוב משחק שלם. לכל דרישה צריכה להיות דרך ברורה לבדוק אותה.

**זמין והודגם:** המיומנות roblox-testing נקראה. [בדיקת הסביבה](../environment-check.md) מתעדת test שנכשל ואז עבר בצד Server ובצד Client, סנכרון Rojo וקריאת Output. זהו תיעוד מהבדיקה הקודמת היום; Studio לא הופעל שוב במסגרת המסמך הזה.

**מקור שנבדק:** [מצבי הבדיקה של Studio](https://create.roblox.com/docs/studio/testing-modes) מתעדים בדיקות עם כמה clients, הדמיית מכשירים ותנאי רשת. הימצאות היכולות בתיעוד אינה הוכחה שהפעלנו אותן דרך MCP.

**הפער והראיה הנדרשת:** עדיין לא אומתו כמה שחקנים, קלט משתמש והדמיית מכשירים בכלים שלנו. עבור מסמך gameplay המאושר נצטרך לכסות איסוף, הגבלת מטען והאטה, הפקדה יחידה, הגבול המדויק של הסגירה, אובדן מטען, סיבוב נוסף, הצטרפות באמצע ועצמאות בין שחקנים. דרושה גם בדיקה של שחקן חדש לאורך סשן. שמירה ורכישות יקבלו בדיקות רק אם ייכנסו למסמך spec מאושר מתאים.

חבילת tests חיצונית לא נבחרה או הותקנה. המיומנות כוללת המלצות והנחות ישנות על runners; אין לאמץ אותן לפני אימות נפרד. לא הודגם כיסוי של המשחק עצמו.

## 4. בניית מסמכים לפי המטרות

**נדרש:** מסמך קצר וקריא שמסביר מה השחקן רואה ועושה, למה זה משרת מטרה, מה בפנים ומה בחוץ, ואיך נבדוק את התוצאה.

**זמין והודגם:** המיומנויות hebrew-content-writer וכן hebrew-rtl-best-practices שימשו לתיעוד. אדם אישר שתצוגת HTML קריאה. קיימים מסמך מטרות וכן spec מאושר; מקור נקי ותצוגת RTL נפרדת הודגמו במסמכים החדשים.

**מקור שנבדק:** [הנחיות Google לכתיבה לפי קהל היעד](https://developers.google.com/tech-writing/one/audience) מדגישות התאמת מילים והסברים לידע של הקורא. אצלנו נשמרים מונחים טכניים באנגלית והכללים המקומיים קובעים את מבנה תהליך SDD.

**הפער והראיה הנדרשת:** אין עדיין מיפוי עקבי מדרישה למטרה ולבדיקה. מסמכים ישנים מסוימים עדיין מכילים תגיות HTML בתוך Markdown; אין להציגם כמקור קריאה תקין בלי תצוגה מתאימה. סגירת הפער תודגם במסמך הרלוונטי הבא, שאדם יוכל להבין ולבדוק ללא הסברים חסרים.

## 5. פירוק למשימות קטנות ושמירת context

**נדרש:** משימה בעלת תוצאה אחת שניתן לבדוק, עם ההקשר הנחוץ והחלטות מתועדות. הפירוק צריך לשמור על משמעות ורצף, ולא לייצר הרבה קבצים או פעולות ללא צורך.

**זמין והודגם:** מסמכי המטרות, מסמך gameplay ומחקר המתחרה מופרדים לפי תפקיד. קיימת היסטוריית commits שניתן לחזור אליה. זה מוכיח שמירת תוצרים, ולא חיסכון בטוקנים או המשכיות מושלמת בין שיחות.

**מקורות שנבדקו:** [Google — שינויים קטנים](https://google.github.io/eng-practices/review/developer/small-cls.html) ממליץ על שינוי עצמאי שניתן להבין ולבדוק. [OpenAI — התאמת skills והוראות](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) מדגיש טעינה מדורגת של ידע וצמצום הוראות שאינן רלוונטיות. המאמר ממוקד במודל מסוים; הוא אינו מדידת עלות לפרויקט שלנו.

**הפער והראיה הנדרשת:** לא בוצע ניסוי המשכיות מתוך מסמך וקבצים בלבד, ולא נמדדו טוקנים לכל משימה. יש גם מתח בין הרצון לצמצם context לבין החובה המקומית לקרוא שבעה קובצי כללים בכל משימה. החובה נשארה בתוקף; שינוי בה אינו חלק מהמסמך. אפשר יהיה להעריך את השיטה לפי הצלחה בהמשך עבודה בלי החלטות שאבדו, קריאה חוזרת או תיקון הנחות שגויות. אין הבטחת חיסכון כמותית.

## 6. מעקב אחר התוכנית וההתאמה למטרות

**נדרש:** לראות מה הושלם, איזו ראיה תומכת בכך, מה חסר, ואיך שינוי משפיע על המטרות ועל מסמך spec. שינוי סטטוס חייב להתבסס על תוצאה.

**זמין והודגם:** כללי SDD וכן Git, תאריכי אישור, דוח סביבה ודוח מחקר עם מגבלות. [מפת המסמכים](../specs/index.md) מציינת תחומים שלא נכנסו למסמך gameplay. אין עדיין implementation plan, ולכן אין ראיה לניטור תוכנית שבוצעה.

**מקור שנבדק:** [Roblox Analytics](https://create.roblox.com/docs/production/analytics) מתאר מעקב אחרי השפעת עדכונים על התנהגות שחקנים. זהו ניטור מוצר; הוא אינו תחליף למעקב אחר ביצוע משימות. שיטת המעקב אחר משימות אצלנו נגזרת מכללי הפרויקט, ולא נטענת כתקן תעשייתי שנבדק.

**הפער והראיה הנדרשת:** בתוכנית עתידית נצטרך לקשר כל משימה לדרישה, לתוצאה ולראיה; לתעד סטייה והחלטה במקום לסמן השלמה לפי עצם כתיבת הקוד. אין כרגע dashboard, ניטור אוטומטי או נתוני שימוש של המשחק שלנו.

## 7. הבנת השחקנים ובדיקת ההנאה

**נדרש:** להבין אם שחקן חדש יודע מה לעשות, מבין את הסיכון ורוצה לצאת לעוד סיבוב. להפריד בין רושם שלנו לבין התנהגות שנצפתה.

**זמין והודגם:** מסמך gameplay כולל שאלות לבחינת ההתלבטות, האזהרה והרצון להמשיך. אפשר לחקור דוגמאות מבחוץ, אך לא נערך playtest עם אנשים והמשחק שלנו עדיין לא ממומש.

**מקורות שנבדקו:** [Onboarding](https://create.roblox.com/docs/production/game-design/onboarding) עוסק בלימוד הבסיס ובהגעה מהירה להנאה; [Prototyping](https://create.roblox.com/docs/production/game-design/prototyping) מתאר בדיקת רעיונות בניסוי מוקדם. אלה עקרונות לבדיקה, לא הוכחה שהרעיון שלנו מהנה.

**הפער והראיה הנדרשת:** קהל היעד ומכשירי היעד המדויקים אינם מוסכמים. דרושה בהמשך תצפית בשחקנים, עם תיעוד של נקודות בלבול, כישלון וחזרה למשחק. Tests אוטומטיים ותמונות אינם יכולים לסגור את הפער הזה.

## 8. הבנת הפלטפורמה, אבטחה וביצועים

**נדרש:** הפרדה בין Server לבין Client, התמודדות עם בקשות מזויפות וניתוקים, מצבי משחק עקביים ומדידת עומס. שמירה בין כניסות תיבדק כאשר תאושר במסגרת שלה.

**זמין והודגם:** המיומנויות roblox-security, roblox-networking וכן roblox-data-stores זמינות. בדיקת הסביבה מתעדת תקשורת בסיסית ותצוגה בצד השחקן. הן אינן ראיה לאבטחה, לריבוי שחקנים או לשמירה תקינה.

**מקור שנבדק:** [אבטחת הגבול בין Client לבין Server](https://create.roblox.com/docs/scripting/security/client-server-boundary) מחייבת אימות נתונים והקשר בצד השרת לפני השימוש בהם. אין להסתפק בכך שהממשק מונע פעולה.

**הפער והראיה הנדרשת:** בהמשך יידרשו בדיקות של איסוף ממרחק לא תקין, בקשות כפולות, בקשות בזמן סגירה וניתוק באמצע פעולה. מדידות של זמן תגובה, זיכרון וקצב תמונה יידרשו בסביבה ובמכשירים שיוגדרו. סוגיית טעינת asset שנרשמה בבדיקת הסביבה עדיין לא אובחנה; אין להציג את הסביבה כנטולת שגיאות.

## 9. חשיבה מוצרית ועסקית

**נדרש:** לבחור היקף שנוכל להשלים, להגדיר מהי הצלחה, ולהעריך מודל הכנסות בלי לפגוע בהנאה. להבחין בין פופולריות, הכנסות ורווח.

**זמין והודגם:** מטרות הפרויקט מוסכמות. במחקר המתחרה נקראו נתוני פעילות ורשימת מוצרים למכירה. לא אומתו הכנסות, מכירות או הסיבה להצלחה.

**מקורות שנבדקו:** [Monetization](https://create.roblox.com/docs/production/monetization) מתאר אפשרויות הכנסה ומזהיר שאין הבטחת הצלחה; [Retention](https://create.roblox.com/docs/production/analytics/retention) מגדיר חזרה למשחק לאחר פרקי זמן. מדריכי המתחרה ונתוניו נבדקו בנפרד במחקר המקושר, ולא הוחלפו בתיעוד של הפלטפורמה.

**הפער והראיה הנדרשת:** לא נקבעו יעדים מספריים, מוצרי תשלום או תקציב מאושר. בהמשך נצטרך לבחור מדדים מתאימים ולבחון נתוני משחק אמיתיים. אין להעביר אלינו מחירים, היקף תוכן או יתרונות בתשלום רק מפני שהם קיימים אצל מתחרה.

## 10. תחזוקה ושימוש חוזר במשחקים נוספים

**נדרש:** מבנה שקל להבין ולשנות, רכיבים בעלי תפקיד ברור והפרדה בין החלטות המשחק לבין מה שבאמת ניתן לשימוש חוזר.

**זמין והודגם:** Git, כללי code review וכן skills זמינים. יש פרויקט בדיקת סביבה מבודד וניתן לשחזור מקומי. עדיין אין רכיבי gameplay שמוכיחים אפשרות לשימוש במשחק נוסף.

**מקור שנבדק:** [Martin Fowler — Yagni](https://martinfowler.com/bliki/Yagni.html), מתאריך 26/05/2015, עוסק בהימנעות מיכולת עתידית משוערת לפני שנדרשת. זהו עיקרון תכנון ותיק שנקרא מחדש היום, ולא מקור עדכני על יכולות Roblox.

**הפער והראיה הנדרשת:** תחזוקה ושימוש חוזר יוכחו כאשר יהיה צורך ממשי בשינוי או בשימוש נוסף, ונוכל לבצעו בלי שכפול ובלי פגיעה בהתנהגות. אין הצדקה להקים framework כללי לפני שיש צורך מוכח. גם אין להבטיח אפס שכפול או אפס תקלות על בסיס מבנה תיקיות בלבד.

## איך לשמור את המיפוי אמין

עדכון נוסף בתאריך 22/10/2026: הושלם סימון החפץ הנבחר ותוקנה חפיפת ההדרכה לכפתור בנייד. שבע חבילות tests עברו בהרצת Server חדשה, ונבדקו הסימון וההפרדה במחשב ובפרופיל נייד מדומה. [ראיות ומגבלות](v1-implementation.md) כוללות גם הסתרת מצלמה שנצפתה פעם אחת ולא שוחזרה בהרצה נוספת. אין עדיין קבלה מלאה.

בכל עבודה רלוונטית נעדכן את התחום שהושפע, את תאריך הבדיקה ואת הקישור לראיה. פער ייחשב סגור רק כאשר קיימת התוצאה הנדרשת; אם משתנים הכלים, המקורות או הדרישות, נבחן אם הראיה עדיין תקפה. המלצות מקורות אינן גוברות על הרשאות אדם וכללי הפרויקט.

**המסקנה כרגע:** מפת הידע והפערים מוכנה לדיון. אין עדיין אישור מוכנות כולל למשחק, ואין צורך להוכיח משחק שלם לפני שמותר לתכנן תחום מאושר. בחירת היקף התוכנית וסגירת הפערים הרלוונטיים לה יהיו החלטות נפרדות עם אדם. במסגרת המסמך הזה לא נוצרה תוכנית מימוש ולא נכתב קוד למשחק.

## עדכון: שילוב השיפור החזותי — 24/10/2026

אדם אישר את השינוי החזותי ואת המשך הבנייה. הדגמים והסביבה עודכנו, ואחת־עשרה חבילות tests עברו בשרת. שלוש הגדרות הבנייה עברו, כולל הפרדת כלי QA מגרסת release.
